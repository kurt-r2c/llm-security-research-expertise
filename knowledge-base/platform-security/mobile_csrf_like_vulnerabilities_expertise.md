# CSRF-Like Vulnerabilities in Mobile Applications: Deep Link Abuse, Intent Spoofing, and WebView Cross-Origin Attacks

> This document synthesizes the mobile CSRF-analogue attack surface — deep-link/URI-scheme hijacking, Android Intent injection and IPC confused-deputy chains, WebView cross-origin and JS-bridge abuse, and mobile OAuth state/token theft — into a single staff-level reference. The core thesis: on mobile, the browser's cross-origin trust boundary is replaced by weaker OS primitives (unauthenticated custom URI schemes, origin-unverifiable Intents, in-process WebView bridges, custom-scheme OAuth redirects), so the classic CSRF confused-deputy pattern reappears in a dozen platform-specific shapes.
>
> Anchored on the published bodies of work of Sergey Toshin / Oversecured (Android intent-redirection, PendingIntent capture, content-provider theft; #1 Google Play + Samsung reward researcher), Promon (StrandHogg 1.0 and StrandHogg 2.0 / CVE-2020-0096 task hijacking), Mohamed Benchikh / Ostorlab ("One Scheme to Rule Them All" OAuth scheme hijacking at scale), Fang Liu et al. (USENIX Security 2017 deep-link measurement study), Chuangang Ren et al. (USENIX Security 2015 task-hijacking formalization), William Denniss & John Bradley (RFC 8252 OAuth 2.0 for Native Apps) and Daniel Fett (RFC 9700 OAuth Security BCP, app2app analysis), WithSecure/MWR Labs (addJavascriptInterface reflection RCE, CVE-2012-6636), Alesandro Ortiz (Android WebView UXSS, CVE-2020-6506), Amol Baikar (Facebook XD Arbiter OAuth token exfil), the OPPO Security Research Team (BlackHat EU 2021 PendingIntent redirection), NCC Group and Bugscale (2024/2025 Samsung deep-link→WebView→RCE chains, the first at Pwn2Own Ireland 2024), Microsoft Threat Intelligence (2026 EngageSDK intent-redirection disclosure), the Chromium Security Team (Android IPC guidance), IMQ Minded Security (MASTG-mapped Semgrep rules), and the OWASP Mobile Application Security Project (MASVS v2 / MASTG).
>

## I. Researcher Profiles

This section anchors every claim in the sections that follow. Each researcher is cited inline where their primitive first appears. Coverage spans four traditions: academic measurement (Liu et al., Ren et al., and the at-scale AsiaCCS/ISSTA studies), commercial mobile application-security-testing research (Oversecured, Ostorlab, Promon, WithSecure, NCC Group, Bugscale), protocol and standards authorship (Denniss and Bradley, Fett), and platform/tooling authority (the Chromium and WebKit security teams, OWASP MASTG, the CodeQL query authors, and IMQ Minded Security). Sergey Toshin/Oversecured and Promon are the two highest-volume anchors for the Android IPC and task-hijacking classes respectively; Benchikh/Ostorlab and the Denniss/Fett standards line anchor the OAuth class.

### Sergey Toshin — Oversecured

Toshin is the founder of [Oversecured](https://oversecured.com/blog/android-deep-link-vulnerabilities) and the single most prolific published author on the Android IPC confused-deputy family. He holds the #1 position in both the Google Play Security Reward Program and the Samsung Mobile security program, with more than $1M in cumulative bounties. His body of work is the taxonomy for this document's Sections II and III: implicit-intent interception, intent redirection, PendingIntent capture, deep-link account takeover, content-provider file theft, and the `HierarchicalUri`/`getHost()` reflection host-spoof (pre-Android-12).

His canonical chains are the reference exploits for the intent-redirection class. Against TikTok and against Google's own Android app (5B+ installs), he demonstrated a chain that begins with intent redirection through an exported proxy, reaches a vulnerable `ContentProvider`, uses a forced `FLAG_GRANT_WRITE_URI_PERMISSION` to overwrite an arbitrary Google Play Core library module in the victim sandbox, and thereby achieves persistent local code execution under the victim's UID. The Google-app instance was reported in February 2021, patched in May, and paid $5,000; it was covered publicly by [Thomas Brewster at Forbes](https://www.forbes.com/sites/thomasbrewster/2021/06/17/google-android-app-with-5-billion-installs-was-vulnerable-to-a-privacy-destroying-hack/). The same chain family recurs across Samsung stock applications, including the SmartThings deep-link auth-token exposure catalogued as CVE-2022-30746 (2022, Samsung SmartThings, unrestricted auth actions plus a deeplink-fed WebView, account takeover).

Toshin also built the Oversecured analysis platform, which operates on compiled APK/AAB (and iOS) artifacts with no source required — 175+ Android and 85+ iOS vulnerability categories. Critically for detection discussion, it is SDK- and merged-manifest-aware: it traces attacker-controlled data from entry points (deep links, intents, QR codes, IPC, local network, SMS) through decompiled code including third-party SDK code, and it recognizes `contains()`-style allowlist bypasses such as `attacker.trusted.com.evil.com`. That merged-manifest coverage is precisely the gap that let the EngageSDK-class exposures ship undetected by source-only SAST.

### Promon research team

Promon (Norway) discovered and named the StrandHogg task-hijacking family. [StrandHogg 1.0](https://promon.io/security-news/the-strandhogg-vulnerability) (December 2019) was tipped by Wultra following in-the-wild Czech banking fraud; it abuses the documented manifest attributes `taskAffinity` and `allowTaskReparenting` (plus `launchMode`) to reparent a spoofed activity onto the victim's task and surface a phishing or permission-prompt overlay. No CVE was assigned because it exploits documented behavior by design, and because it is manifest-declared it is statically detectable at Play submission. Lookout identified roughly 36 malicious apps exploiting it in the wild (disclosed alongside Promon's writeup), targeting 60 financial institutions.

[StrandHogg 2.0](https://promon.io/resources/downloads/strandhogg-2-0-new-serious-android-vulnerability) is CVE-2020-0096 (May 2020, Google-rated critical). It achieves the identical credential/permission-overlay outcome through runtime reflection with no manifest `taskAffinity` marker, is therefore far harder to detect statically, and can attack nearly all apps on a device simultaneously without per-target configuration. It affected devices through Android 9 (~91.8% of the fleet at disclosure) and was patched in the September 2020 bulletin; Android 11 (API 30) contains the structural fix. Note that CVE-2019-2215 — a Binder use-after-free — is frequently conflated with StrandHogg in secondary sources but is unrelated.

### Chuangang Ren et al. — Penn State / FireEye

Ren and colleagues published the original formal analysis of Android task-reparenting and `taskAffinity` as a security attack primitive at USENIX Security 2015. This is the foundational academic work that StrandHogg operationalized four years later, and it is [referenced by Google's own StrandHogg risk documentation](https://developer.android.com/privacy-and-security/risks/strandhogg). The paper established that task-management semantics — designed for UX continuity — could be weaponized to insert attacker activities into a victim's back stack.

### Mohamed Benchikh — Ostorlab

Benchikh authored [*One Scheme to Rule Them All*](https://blog.ostorlab.co/one-scheme-to-rule-them-all.html) (2023), the modern at-scale demonstration of OAuth account takeover via custom-scheme hijacking. His central finding is that PKCE is defeated not by breaking the cryptographic binding but by upstream redirect-host validation failures: Facebook accepted `fbconnect://cct.com.<fake>` because the host was unvalidated against the same `client_id`, and setting `login_hint` to the victim's email produced zero-interaction interception. His analysis spans Google, Facebook, Amazon Cognito, and Okta flows and includes a 3.5B-download social platform that acknowledged the issue.

### Fang Liu, Chun Wang, Andres Pico, Danfeng Yao, Gang Wang — Virginia Tech / University of Illinois

This group authored [*Measuring the Insecurity of Mobile Deep Links of Android*](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-liu.pdf) at USENIX Security 2017, the foundational measurement study for the deep-link class. Their key empirical result is that of 8,878 App-Link-declaring apps, only ~194 (2.2%) verified correctly — meaning the OS-enforced domain-ownership mechanism that closes scheme squatting by design was, in practice, almost universally unadopted or misconfigured. They further showed that scheme URLs remained freely hijackable and that newer linking methods, as deployed, worsened security rather than improving it.

### William Denniss and John Bradley — Google / Ping Identity (IETF OAuth WG)

Denniss and Bradley authored [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html), *OAuth 2.0 for Native Apps* (BCP 212). It codified the custom-scheme interception risk that this document's Section V treats in depth, prohibited embedded user-agents (WebViews) for authorization in §8.12, and mandated PKCE for public native clients, preferring claimed-`https` redirects where possible. It defines the AppAuth pattern — system browser via `ASWebAuthenticationSession` (iOS) or Chrome Custom Tabs (Android), PKCE `S256`, and validated `state`. Denniss is also an author of the AppAuth libraries.

### Daniel Fett — yes.com

Fett, with Fabian Hauck and Joseph Heenan, wrote an [analysis of mobile app-to-app OAuth security](https://danielfett.de/2020/11/27/improving-app2app/) (2020): code-injection risks, the iOS `universalLinksOnly` plus `ASWebAuthenticationSession` workaround, and Android App Links guidance. He is a co-author of RFC 9700 (*OAuth 2.0 Security Best Current Practice*, 2025), whose §2.1.1 mandates symmetric PKCE enforcement — servers MUST reject token requests carrying a `code_verifier` unless a `code_challenge` was present at authorization time, and public clients require PKCE unconditionally with `S256` the only method that does not expose the verifier (`plain` not recommended). This directly closes the PKCE-downgrade class treated in Section V.

### WithSecure Labs (formerly MWR InfoSecurity)

WithSecure produced the foundational [WebView `addJavascriptInterface` remote code execution research](https://labs.withsecure.com/publications/webview-addjavascriptinterface-remote-code-execution) that defines the Android JS-bridge RCE class. The technique uses the Java Reflection API over any injected interface object — `getClass().forName(...).getRuntime().exec(...)` — to run arbitrary OS commands with the host app's permissions on Android API < 17, covered by CVE-2012-6636 and CVE-2013-4710. The work drove the API-17 `@JavascriptInterface` annotation boundary and the Metasploit `webview_addjavascriptinterface` module. WithSecure also authored the CVE-2018-9524 MediaProjection tapjacking advisory (2017), a consent-bypass affecting ~77% of devices at the time.

### Alesandro Ortiz — independent

Ortiz discovered [CVE-2020-6506](https://alesandroortiz.com/articles/uxss-android-webview-cve-2020-6506/) (2020, Android WebView, universal cross-site scripting), the UXSS arising when `setSupportMultipleWindows(false)` causes WebView to treat `window.open('javascript:PAYLOAD')` the same as an `https://` navigation — navigating the top document and executing attacker JS in its origin. ### Amol Baikar — independent

Baikar discovered a ten-year-old [Facebook OAuth vulnerability](https://gbhackers.com/facebook-vulnerability/) (2020, $55,000 bounty): a missing `X-Frame-Options` header combined with improper `window.parent` cross-domain `postMessage` handling let a malicious site frame the login flow and receive the access token via the XD Arbiter event with no victim interaction. ### OPPO Security Research Team

The OPPO team systematized PendingIntent redirection as a universal privilege-escalation method in their [BlackHat EU 2021 talk](https://segmentfault.com/a/1190000041550819/en). ### Microsoft Threat Intelligence

Microsoft's [April 2026 disclosure](https://www.microsoft.com/en-us/security/blog/2026/04/09/intent-redirection-vulnerability-third-party-sdk-android/) documented an intent-redirection flaw in EngageLab's EngageSDK (30M+ wallet installs). The exported `MTCommonActivity` — exposed via merged manifest — parsed `n_intent_uri` from attacker-supplied data using `Intent.parseUri()` with `URI_ALLOW_UNSAFE`, then granted `FLAG_GRANT_PERSISTABLE_URI_PERMISSION | FLAG_GRANT_READ_URI_PERMISSION | FLAG_GRANT_WRITE_URI_PERMISSION` to the attacker's app — persistent read/write access to the victim's private storage. Fixed in EngageSDK v5.2.1 (November 2025). It is recent proof the class remains live post-Android-12, and specifically that API-31 exported enforcement does not touch SDK-merged exposure.

### Chromium Security Team — Google

The Chromium team authored the canonical architectural statement in the [Android IPC security guide](https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/docs/security/android-ipc.md): "It is fundamentally impossible to determine the sender of an Intent, unless the Activity was started with `startActivityForResult`." `Binder.getCallingUid()` returns caller identity only inside an active Binder transaction (Service/ContentProvider IPC, non-`FLAG_ONEWAY` AIDL) — for an Intent delivered to an Activity, execution runs on the main thread outside any Binder transaction, so `getCallingUid()` returns the recipient's own UID. This property is load-bearing for the entire Android CSRF-analogue argument: permission checks decide whether access is allowed, never who the caller is.

IMQ Minded Security published [40+ MASTG-derived Semgrep rules for Android SAST](https://blog.mindedsecurity.com/2023/10/semgrep-rules-for-android-application.html) (`mindedsecurity/semgrep-rules-android-security`), benchmarked against 280 apps totaling 111B+ downloads and producing 107,173 findings (~382/app). Coverage includes `setAllowUniversalAccessFromFileURLs`, JS-plus-bridge combinations, `onReceivedSslError` `proceed()`, and SSL-pinning misconfiguration in both `network_security_config.xml` and Java source. ### OWASP Mobile Application Security Project

The [OWASP MAS project](https://mas.owasp.org/) provides MASVS v2 (MASVS-PLATFORM-1 for IPC and deep links; MASVS-PLATFORM-2 for WebViews) and the MASTG test-case catalog — the shared vocabulary for mobile CSRF-analogue testing. ## II. Deep Link Abuse as CSRF

### Custom URI scheme hijacking — the foundational confused-deputy primitive

Custom URI schemes date to Android 1.0 and iOS 2.0 and were designed for inter-app flexibility, not authenticity. Any application may register any scheme — on Android via `<intent-filter android:scheme="...">`, on iOS via `CFBundleURLSchemes` — with no proof of ownership of the string. A co-installed malicious app that registers a victim's scheme intercepts whatever that scheme carries: OAuth authorization codes, magic-link and password-reset tokens, session identifiers. This is the root confused-deputy / CSRF-analogue primitive underlying every subsequent deep-link finding: the OS silently routes attacker-influenced input to a deputy that then acts on it, with no per-message authenticity binding.

Resolution semantics differ by platform and worsen the picture. On Android the OS may silently route the URI or present a disambiguation chooser; an attacker biases selection by declaring a high `android:priority` on the intent-filter (though decisively overriding another app's activity generally requires a system app, broad implicit-intent and broadcast interception is available to ordinary third-party apps). On older iOS, resolution is undefined when multiple apps claim the same scheme — the behavior FireEye documented in its 2015 iOS URL-scheme-hijacking / Masque work. There is no CVE for the base class because it is a design property, later formalized as a risk by RFC 8252 and enumerated in Android's ["unsafe use of deep links"](https://developer.android.com/privacy-and-security/risks/unsafe-use-of-deeplinks) guidance and OWASP MASTG-TEST-0393.

### Verified deep links and their fragile verification

Android App Links (2015, `android:autoVerify`) and iOS Universal Links (iOS 9) replace unverifiable schemes with `http(s)` links plus OS-enforced domain-ownership proof. Android fetches `/.well-known/assetlinks.json` and matches SHA-256 package signing fingerprints; iOS fetches `apple-app-site-association` (AASA) and matches the `applinks:` entitlement App-ID. Correctly deployed, this closes scheme squatting by design — a competing app cannot claim a domain it does not control.

In practice the mechanism is fragile and mostly unadopted. Liu et al. (USENIX 2017) measured only ~194 of 8,878 App-Link apps (2.2%) verifying correctly. Verification silently downgrades to plain-web-URL handling — falling back to the browser or an interceptable scheme — on any of several conditions: an AASA/`assetlinks.json` served over a redirect, non-HTTPS delivery, IP-restricted access, or an App-ID/fingerprint mismatch. The iOS failure mode is particularly quiet: iOS treats a misconfigured Universal Link as an ordinary web link with no error surfaced to the user or developer.

Crucially, origin verification passing does not imply the parameters are safe. A verified link whose AASA uses a wildcard `'/*'` path pattern, combined with a handler that trusts path or query parameters without sanitization, is a CSRF/injection entry point even though the domain-origin check succeeded — the case OWASP captures as MASTG-TEST-0395. The `application(_:continue:restorationHandler:)` handler receives the full URL, and any downstream trust in its components reopens the attack surface that Universal Links were supposed to close.

### OAuth redirect_uri interception via custom-scheme deep link

Mobile OAuth commonly uses a custom-scheme `redirect_uri` — `com.googleusercontent.apps.<id>://oauthredirect`, `fbconnect://`, `myapp://callback?code=...`. A malicious app registering the same scheme receives the authorization response and exchanges the code for tokens. This is the canonical mobile OAuth bug class. RFC 8252 §8.1 notes that multiple apps can register the same private-use scheme, §7.2 prefers claimed-`https` (App Link/Universal Link) redirects where possible, and §8.1 states that the authorization server should reject code requests lacking PKCE parameters. PKCE (RFC 7636) binds the code to the originating client's `code_verifier`, so an intercepted code alone is worthless to the attacker.

On iOS this is the primary residual gap. AppAuth-iOS [issue #396](https://github.com/openid/AppAuth-iOS/issues/396) documents that Universal Links require a user tap rather than an automatic redirect in in-app browser tabs, which makes them unreliable as OAuth redirect handlers. Custom schemes therefore remain the only viable redirect mechanism on iOS, and PKCE plus `state` are the sole compensating controls against scheme hijacking. This is an unresolved platform gap rather than a developer error.

### PKCE-bypass variants — token-in-fragment leak and unvalidated redirect host

PKCE is not a universal guard. It does nothing for flows that leak both the code and the access token in the redirect fragment — for example `https://auth.expo.io/@acct/proj#code=...&access_token=...` bounced to an `exp://` scheme, where the token is present regardless of any `code_verifier` check. And it is defeated upstream by redirect-host validation failures. Benchikh's *One Scheme to Rule Them All* showed Facebook accepting `fbconnect://cct.com.<fake>` because the host was unvalidated while sharing the legitimate `client_id`; setting `login_hint` to the victim's email produced zero-interaction interception.

This is the same class the ~2013–2015 Facebook OAuth custom-scheme era originated — mobile apps using `fbconnect`-scheme callbacks with host-based differentiation, where the backend did not fully validate the callback host, letting an attacker substitute a host under a scheme sharing the legitimate `client_id`. The 2023 Ostorlab work is the same bug re-demonstrated at scale a decade later. The fix is strict exact-match `redirect_uri` validation across scheme, host, and path, and never returning tokens in interceptable redirects — as [Doyensec's 2025 OAuth writeup](https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html) reiterates.

### Real-world deep-link → account-takeover corpus

The impact class is well-established in disclosed research and bug-bounty reports. CVE-2022-30746 (2022, Samsung SmartThings, Oversecured): unrestricted auth actions (`REQUEST_AUTH_CODE`, `WEB_AUTH_MANAGER`, `ACTION_WEBVIEW_WITH_PASSWORD_EXTERNAL`) combined with a deeplink-fed WebView exposed the auth-code flow to any third-party app, yielding account takeover. CVE-2024-26131 (2024, Element Android): intent redirection let a third-party app launch internal screens, enabling arbitrary web-page display and a login-screen account takeover.

The public HackerOne corpus maps the primitives to real one- and two-click takeovers: #1667998 (KAYAK, session-cookie theft via malicious deeplink, patched v161.2); #1500614 (TikTok, one-click ATO via an unvalidated parameter reaching a WebView JavaScript interface); #3079738 (Basecamp/HEY, `Authorization` Bearer token leaked to an attacker server on an Undo action); #855618 (Arrive/Shop, Branch.io magic-link login token passed via an unverified deeplink and intercepted); and #401793 (Grab, arbitrary attacker URL loaded into a WebView → sensitive-info disclosure).

## III. Android Intent Spoofing and IPC Attacks

### The confused-deputy base class: exported components without a permission guard

A component declared `android:exported="true"` — or, targeting API < 31, implicitly exported because it declares an `<intent-filter>` — with no `android:permission` is directly invocable by any installed app via `startActivity`/`startService`/`sendBroadcast`/`bindService`. The invoked component runs under the victim app's UID and permissions. This is the direct CSRF analogue: the attacker supplies a forged request (an Intent), the deputy acts on it under privileged context, and there is no per-request authenticity check — no CSRF token, and no caller-identity verification. If the component performs a privileged action (writes to the app sandbox, sends SMS, initiates a call, mutates state), an unprivileged attacker rides the victim's authority. CWE-926 (Improper Export of Android Application Components) and CWE-749 name the class.

The reason authorization cannot be reconstructed from the Intent itself is the Chromium team's architectural property: the Intent sender is fundamentally unverifiable for Activities. `Binder.getCallingUid()` returns caller identity only inside an active Binder transaction — Service or ContentProvider IPC — never for Activity Intent delivery, where execution runs on the main thread outside any transaction and the call returns the recipient's own UID. The correct pattern therefore requires both an exported gate and either a signature-`protectionLevel` `android:permission` or an in-handler `Binder.getCallingUid()`/`getCallingPackage()` check inside a Service/ContentProvider context; Intent extras must never be trusted for authorization.

### Implicit-intent interception and android:priority ordering

An implicit intent — action/category/data set, no explicit component or package — is resolved by intent-filter matching across all installed apps. A malicious app that registers a matching action, scheme, or MIME type is eligible to receive the intent and capture sensitive extras (tokens, PII, deep-link auth codes) or, for broadcasts, eavesdrop on the payload. This is the CSRF-like inversion: rather than the attacker forging an inbound request, the victim's own outbound request is redirected into attacker-controlled code. Toshin's [implicit-intent interception research](https://blog.oversecured.com/Interception-of-Android-implicit-intents/) catalogues the pattern in production apps.

`android:priority` orders handlers for implicit intents (higher wins, default 0). Decisively overriding another app's activity via priority generally requires a system app, but broad implicit-intent and broadcast interception is abusable by ordinary third-party apps, and ordered broadcasts can be intercepted and aborted or mutated by a higher-priority malicious receiver (see CommonsWare's "Troubling Tale of android:priority"). Host validation is a recurring weak point: `startsWith()`/`contains()`/`endsWith()` checks are bypassable with `https://trusted.com@attacker.com/` or `trusted.com.attacker.com`, and expired whitelisted domains can be re-registered by an attacker. The defenses are explicit intents (`setPackage`/`setComponent`), `LocalBroadcastManager` for internal broadcasts, verified App Links, and exact-match host validation.

### Intent redirection — the dominant IPC-CSRF primitive

Intent redirection is the dominant Android IPC-CSRF primitive. Because `Intent` implements `Parcelable`, an Intent can be nested as an extra inside another Intent. An exported proxy component extracts the nested Intent via `getParcelableExtra(...)` (or parses an `intent://` URI via `Intent.parseUri()`) and forwards it to a dangerous sink — `startActivity`/`startService`/`sendBroadcast`/`bindService` — without validating the target. The redispatched intent executes under the victim's UID, which grants the attacker three escalations: reaching the victim's non-exported components (which the attacker could not launch directly); forcing `FLAG_GRANT_READ_URI_PERMISSION`/`FLAG_GRANT_WRITE_URI_PERMISSION` so the victim grants the attacker access to its own non-exported ContentProviders (arbitrary sandbox file read/write); and chaining into code execution by overwriting dynamically-loaded modules (dex/jar/so). Oversecured has stated that a majority of apps historically contained some form of it.

Toshin's canonical chains are the reference: against TikTok and Google's own Android app (5B+ installs), intent redirection reached a vulnerable ContentProvider, forced a write URI grant to overwrite a Google Play Core library module, and achieved persistent local code execution ($5,000 on the Google app). The class remains live post-Android-12: Microsoft's April 2026 EngageSDK disclosure (30M+ wallet installs) showed an exported `MTCommonActivity` parsing `n_intent_uri` via `Intent.parseUri(URI_ALLOW_UNSAFE)` and then granting `FLAG_GRANT_PERSISTABLE_URI_PERMISSION` plus read/write URI permissions to the attacker — fixed in v5.2.1. The WebView variant runs `Intent.parseUri()` on attacker-controlled `intent://` URIs and calls `startActivity()`; an "intent selector" bypass sets the selector field to reach a component even when the component field is blocked. The fix is to never forward untrusted Intents — and where unavoidable, to strip component and selector, clear `FLAG_GRANT_*` URI flags, validate the resolved target against an allowlist, and check caller identity (see [Ostorlab's intent-redirection writeup](https://blog.ostorlab.co/) and AndroidX `IntentSanitizer`).

### PendingIntent capture — delegated-authority token abuse

A PendingIntent lets the recipient later fire the wrapped intent with the creator's identity and permissions — the closest Android analogue to a bearer credential, a delegated-authority capability token. Two shapes are dangerous. First, an implicit base Intent (no component or package): when the holder calls `send()` with a `fillInIntent`, `Intent.fillIn()` supplies the missing fields — it overwrites every field that is EMPTY in the base except component and selector, which require explicit `FILL_IN_COMPONENT`/`FILL_IN_SELECTOR` flags. Second, `FLAG_MUTABLE` (or, on API < 23, no flag): the holder rewrites unfilled fields to point at the creator's non-exported components or ContentProviders and to add `FLAG_GRANT_READ/WRITE_URI_PERMISSION`. Attackers obtain the tokens through legitimate channels — notifications (`NotificationListenerService`), Slices/`SliceProvider`, `MediaBrowserService`, or app widgets; [arXiv:2603.02539](https://arxiv.org/pdf/2603.02539) (PendingIntent Provenance Confusion) documents replaying a partner app's PendingIntent to impersonate it in SDK authentication flows with no platform exploit required.

The AOSP corpus, systematized by the OPPO team at BlackHat EU 2021, comprises CVE-2020-0188 (2020, SettingsSliceProvider), CVE-2020-0389 (2020, SystemUI RecordingService notification), CVE-2020-0294 (2020, system service management interface), and A-166126300 (BluetoothMediaBrowserService); CVE-2021-0928 (2021, AOSP, A-188675581, CVSS 7.8) is the associated `OutputConfiguration` serialize/deserialize hardening bug (CWE-20/CWE-755). This research drove Google Play's "Implicit PendingIntent Vulnerability" ASI program and the Android 12 requirement that every PendingIntent explicitly declare `FLAG_IMMUTABLE` or `FLAG_MUTABLE` or the framework throws. Detection is served by OPPO's static detector and PITracker (WiSec 2022); the fix is `FLAG_IMMUTABLE` plus an explicit base Intent (MASTG-TEST-0381).

### Content-provider path traversal, broadcast spoofing, and framework confused-deputy

A `FileProvider` (or other ContentProvider) implementing `openFile()`/`openAssetFile()`/`query()` without canonicalizing the incoming `Uri` path lets a crafted `content://` URI containing `../` escape the intended shared directory and return a `ParcelFileDescriptor` for arbitrary files readable by the provider's UID — `databases/secret.db`, `shared_prefs`, cached tokens. Two delivery paths exist: the provider is exported or misconfigured and queried directly, or the attacker reaches it via intent redirection plus a forced `FLAG_GRANT_READ_URI_PERMISSION`. A symmetric variant is a consuming app improperly trusting a filename returned by an untrusted provider. Root causes overlap on `android:grantUriPermissions="true"` with a broad `<root-path>` or `<files-path path="">`; Google Play's "Path Traversal Vulnerability" ASI program ([answer/7496913](https://support.google.com/faqs/answer/7496913)) and Android's "untrustworthy-contentprovider-provided-filename" risk doc catalogue both directions. The fix is path canonicalization with a fixed-base `getCanonicalPath` prefix check, narrowly scoped FileProvider roots, and `exported="false"` where sharing is not required.

Exported BroadcastReceivers without a receiver permission produce two problems. Spoofing: an attacker forges a broadcast — including impersonating an app-defined action, since ordinary broadcasts can be faked — to drive privileged state changes. Eavesdropping/hijacking: sensitive data broadcast without an enforced receiver permission is readable by any registered listener, and ordered broadcasts are interceptable by a higher-priority receiver. Protected system broadcasts (`BOOT_COMPLETED` and the like) can only be sent by the system, but most app-defined actions are unprotected. The defenses are `LocalBroadcastManager` or explicit-package broadcasts for internal comms, signature-`protectionLevel` permissions on exported receivers, and a `receiverPermission` on sensitive sends.

The same confused-deputy pattern appears at the framework level. CVE-2022-20223 (2022, Android 10–12L): a flaw in `assertSafeToStartCustomActivity()` in `AppRestrictionsFragment.java` lets an app place a phone call without holding `CALL_PHONE` by abusing the restricted-profile activity-start path — a trusted framework component starting an action derived from attacker-influenced input without adequately re-checking authority.

### Task hijacking (StrandHogg 1.0 / 2.0) and tapjacking

Task hijacking redirects user trust rather than a message. StrandHogg 1.0 (Promon, December 2019, no CVE) abuses the documented attributes `taskAffinity` (set to the victim's package) plus `allowTaskReparenting="true"` and `launchMode` to reparent a spoofed activity into the victim's task; tapping the legitimate icon surfaces the attacker's phishing overlay to harvest credentials, or hijacks a permission prompt. Because it is manifest-declared it is statically detectable at Play submission; Lookout identified 36 malicious apps exploiting it in the wild, including BankBot banking-trojan variants. The primitive was formalized by Ren et al. at USENIX Security 2015.

StrandHogg 2.0 is CVE-2020-0096 (Promon, May 2020, Google-critical): the same credential/permission-overlay outcome achieved via runtime reflection with no manifest marker, far harder to detect statically, and able to attack nearly all apps at once. It affected devices through Android 9 (~91.8% of the fleet) and was patched in the May 2020 bulletin. CVE-2019-2215 (a Binder use-after-free) is unrelated and is frequently conflated in secondary sources.

Tapjacking is the adjacent overlay attack: a malicious window (`SYSTEM_ALERT_WINDOW` / `TYPE_APPLICATION_OVERLAY`) sits atop the victim UI and passes touches through, tricking the user into approving actions or consents. It is defended with `android:filterTouchesWhenObscured="true"` (or `onFilterTouchEventForSecurity`), which makes obscured touches drop. The broader task-hijacking defenses are `launchMode` `singleInstance`/`singleTask` plus an empty `taskAffinity=""` on sensitive activities, a `minSdkVersion` of 30, current patch level, and runtime overlay/task-state anomaly detection.

### What Android 12 (API 31) exported enforcement fixes — and does not

Apps targeting Android 12 must explicitly set `android:exported` on any activity, service, or receiver declaring an `<intent-filter>`, or the build fails. This kills the historic footgun where declaring an intent-filter implicitly defaulted the component to `exported=true`, silently exposing components developers assumed were private — a secure-by-default, force-a-decision change.

It does not add an access-control mechanism. A component the developer legitimately sets `exported="true"` remains callable by any app unless separately guarded by an `android:permission` and/or an in-code caller check. It does nothing for intent redirection, PendingIntent mutability, content-provider path traversal, scheme/deep-link hijacking, task hijacking, or WebView bridges, and SDK manifest merging can still introduce `exported=true` from a library manifest — exactly how EngageSDK shipped its exposure. The `protectionLevel` remains load-bearing: only `SIGNATURE` reliably restricts callers to the same signing certificate; `NORMAL` is auto-granted at install (essentially no barrier), `DANGEROUS` is user-grantable (bypassable by request plus consent, or social engineering), and custom-permission-definition races exist where a malicious app declares the same permission name first. The correct pattern is explicit `exported` declaration plus a signature-`protectionLevel` permission plus `Binder.getCallingUid()`/`getCallingPackage()` verification inside a Service/ContentProvider context (see Android's ["let's be explicit about our intent filters"](https://medium.com/androiddevelopers/lets-be-explicit-about-our-intent-filters) and SEI CMU DRD07-X).

## IV. WebView CSRF and Cross-Origin Mobile Attacks

The WebView is where the browser's origin model and the mobile OS's IPC model collide, and it inherits the weaknesses of both. A WebView is an in-app browser that renders attacker-influenceable content while sitting inside the host app's trust boundary — it carries the app's authenticated cookies, it can be handed a JS-to-native bridge that reaches privileged capability, and on both platforms the bridge is injected into *every* frame with no default origin check. The result is that the classic CSRF confused-deputy pattern (a request issued in the victim's authenticated context by attacker-controlled content) reappears, but with escalation paths — sandbox file read, native method invocation, arbitrary activity launch — that a browser CSRF never had. The through-line of this section: any primitive that lands JavaScript execution in an app's WebView (a deep-link-navigated URL, an empty-`baseURL` `loadHTMLString`, a UXSS) is not a low-severity web bug on mobile; it is the pivot that reaches the sandbox and the native bridge.

### addJavascriptInterface reflection RCE — the canonical JS-bridge class

The founding vulnerability of the class is `WebView.addJavascriptInterface()` on Android API < 17 (Android 4.2). The method exposes an entire injected Java object to loaded JavaScript, and because the exposure was unrestricted, untrusted content could walk the Java Reflection API off any injected object — `this.getClass().forName("java.lang.Runtime").getMethod("getRuntime",...).invoke(null).exec(...)` — to execute arbitrary OS commands with the host app's UID and permissions. The interface is injected into every frame including cross-origin `<iframe>`s, so a MITM on cleartext HTTP, a malicious ad frame, or persistent XSS in loaded content all reach it. **CVE-2012-6636** (2013, Android WebView `addJavascriptInterface`, arbitrary code execution) and the related **CVE-2013-4710** anchor the class; the technique is covered in WithSecure/MWR Labs' foundational [WebView addJavascriptInterface RCE research](https://labs.withsecure.com/publications/webview-addjavascriptinterface-remote-code-execution) and ships as Metasploit's `android/browser/webview_addjavascriptinterface` module.

API 17+ closed the reflection path by requiring the `@JavascriptInterface` annotation to gate which methods are callable from JS, which kills the `getClass()`-to-`Runtime.exec` walk. It does **not** close three residual exposures: (a) an app still declaring `minSdkVersion`/`targetSdk` < 17; (b) an annotated method that itself performs a sensitive operation (`getAuthToken()`, `readFile()`); and (c) any content the WebView loads that an attacker can influence over MITM, mixed content, or an intent-redirected URL. The load-bearing dangerous combination — the one a Semgrep rule should chase — is an **exported Activity + `setJavaScriptEnabled(true)` + `addJavascriptInterface(obj, name)` + `loadUrl(getIntent().getStringExtra("url"))`**: an attacker sends an Intent with a malicious URL as an extra, the exported Activity loads it, and the attacker's JS calls the annotated bridge methods. This is [MASTG-TEST-0033](https://mas.owasp.org/MASTG/tests/android/MASVS-PLATFORM/MASTG-TEST-0033/) (Java objects exposed through WebViews) and is scored by CodeQL's `java/android/webview-addjavascriptinterface` query (CWE-79, severity raised to 7.8 in CodeQL 2.25.2).

### UXSS, file:// SOP bypass, and local file exfiltration

Even with the reflection path closed, the WebView's same-origin enforcement is exploitable. **CVE-2020-6506** (2020, Android System WebView, universal XSS; discovered by [Alesandro Ortiz](https://alesandroortiz.com/articles/uxss-android-webview-cve-2020-6506/)) exploits `WebSettings.setSupportMultipleWindows(false)` — the default — under which the WebView treats `window.open()` to a `javascript:` URL identically to an `https://` URL and navigates the **top document** to it. A cross-origin iframe can therefore call `window.open('javascript:PAYLOAD')` and execute in the top-level document's origin: universal XSS. It normally costs one tap, but becomes a **zero-interaction drive-by** when the top page is `file://` and both `setJavaScriptCanOpenWindowsAutomatically(true)` and `setAllowUniversalAccessFromFileURLs(true)` are set. Affected WebView 76.0.3809.21-beta through 83.0.4103.105, fixed in 83.0.4103.106 (June 2020); it flows directly into `react-native-webview` apps that navigate to arbitrary URLs (**GHSA-36j3-xxf7-4pqg**).

The exfiltration primitive underneath is the `file://` same-origin collapse. `setAllowUniversalAccessFromFileURLs(true)` lets JS running under a `file://` origin read content from *any* origin (`https://`, `content://`, `file://`), so an XSS or attacker-controlled `file://` page can `XHR`/`fetch` the app's private `/data/data/<pkg>/` files — SQLite databases, `shared_prefs` XML, session tokens — and `POST` them out. `setAllowFileAccessFromFileURLs(true)` is the narrower file-to-file variant. Both default `false` on modern Android and were deprecated at API 30. On iOS the equivalent hazard is subtler: a `WKWebView`/`UIWebView` `loadHTMLString(html, baseURL:)` call with an **empty or nil `baseURL`** silently promotes the content to the `file://` origin, so any XSS in that HTML reads the sandbox (Allyson O'Malley, [iOS Bug Hunting — Web View XSS](https://www.allysonomalley.com/2018/12/03/ios-bug-hunting-web-view-xss/), 2018). Legacy `UIWebView` is worse still: `WebKitAllowUniversalAccessFromFileURLs` / `WebKitAllowFileAccessFromFileURLs` are **on by default** and its `file://` handling ignores SOP unconditionally. The SOP-restoring fixes are `WebViewAssetLoader` on Android (serves local assets over a synthetic `https://` origin) and a real non-`file` `baseURL` on iOS; CodeQL's `java/android/unsafe-android-webview-fetch` (CWE-749) traces the intent-extra-to-`loadUrl` taint with these flags enabled.

### Native-bridge over-exposure and the file:// + bridge combined chain

Both bridges — Android `addJavascriptInterface` and iOS `WKUserContentController.add(handler, name:)` reachable from JS as `window.webkit.messageHandlers.X.postMessage(...)` — are reachable from **any page or frame** loaded in the WebView with **no built-in origin check**. A deep-link-navigated attacker page or an embedded iframe inherits full bridge access; risk scales with how many and how powerful the exposed methods are and whether their arguments are validated. The highest-impact composition stacks the two primitives: a `file://` page (sandbox read) **plus** an exposed bridge (native method invocation). An attacker who lands any JS-execution primitive — deep-link XSS, empty-`baseURL` `loadHTMLString`, malicious downloaded HTML, or a UXSS like CVE-2020-6506 — can then both exfiltrate private files and invoke privileged native calls. This is the pivot that turns a web bug into full app compromise, and it is why the Android platform docs describe native bridges as "sharp knives" and Ostorlab's [WebView bridge-exposure research](https://blog.ostorlab.co/webviews-security-android-ios.html) treats missing origin validation as the central defect. On iOS there is an additional lifecycle footgun: failing to call `removeScriptMessageHandler` on teardown retains the `WKWebView` (a retain-cycle leak) and can leave a stale bridge live; correct practice validates `message.frameInfo`/`securityOrigin` and the arguments on every call ([MASTG-TEST-0078](https://mas.owasp.org/MASTG/tests/ios/MASVS-PLATFORM/MASTG-TEST-0078/)). The defensive posture is uniform: origin-gate every bridge call against an allowlist (`webView.url` host check before honoring a message), keep the handler surface minimal, and structurally separate untrusted-content WebViews from bridged ones.

### WKWebView vs UIWebView vs SFSafariViewController/ASWebAuthenticationSession trust boundaries

The choice of WebView class is itself a trust-boundary decision. `UIWebView` (deprecated iOS 12) renders the web engine **in-process** with the app — a WebContent memory-corruption bug compromises the app process directly — and ships with file/universal access on by default and SOP ignored for `file://`; any 2026-era `UIWebView` usage is a finding on its own merits, and the App Store rejects new usage. `WKWebView` renders **out-of-process** in an isolated WebContent process, refuses `XHR` to `file://` by default (CORS-enforced), and defaults `allowFileAccessFromFileURLs`/`allowUniversalAccessFromFileURLs` to `false` — but it is fundamentally **app-controlled and app-visible**: the host app can inject JS, read the DOM, register bridges, and scrape credentials, and it exposes no address bar or TLS indicator, so users have no anti-phishing cue. `SFSafariViewController` runs Safari's engine in a **separate process** with a real URL bar, TLS indicator, phishing protection, and (since iOS 11) a cookie/website-data store isolated from both Safari and the host app, which cannot read its cookies, DOM, or credentials. `ASWebAuthenticationSession` is the sanctioned auth agent: it shares Safari's cookie store for SSO while structurally shielding credentials from the app. The rule that falls out — and it is mandated by [RFC 8252 §8.12](https://www.rfc-editor.org/rfc/rfc8252.html#section-8.12) — is that OAuth/OIDC and any third-party credential entry must never occur in an app-controlled `WKWebView`/`UIWebView`; use `ASWebAuthenticationSession` (auth) or `SFSafariViewController` (trusted external browsing), and reserve `WKWebView` for first-party content the app fully controls.

### WebView CSRF, SameSite semantics, and network-layer bypasses

A malicious page loaded in an authenticated WebView can issue state-changing requests that carry the app's session cookies — textbook CSRF — and the browser-side mitigation, `SameSite`, is both inconsistent in WebViews and structurally incomplete on mobile. `WKWebView` rides the iOS networking stack and has accumulated cookie regressions across releases: iOS 12 treated `SameSite=None` as `Strict`; iOS 13/13.3/14 omitted cookies on cross-origin requests and image loads ([WebKit bugs 200857, 204109, 213510](https://bugs.webkit.org/show_bug.cgi?id=213510)). Android WebView was deliberately excluded from Chrome 80's `SameSite` enforcement for compatibility and only got modern behavior (`no-attribute` = `Lax`, `None` requires `Secure`) for apps targeting API 31+. Three limits make `SameSite=Lax` defense-in-depth only: it does nothing against **same-site** attacker content (a compromised subdomain on the same registrable domain), it still permits top-level GET navigations, and — critically on mobile — it does **not** stop intent injection, because an exported-Activity-driven WebView controls the loaded URL's origin directly and thereby bypasses `SameSite` entirely (`SameSite` protects cookie *transport*, not the navigation *origin*). OWASP's position holds: pair `SameSite`+`HttpOnly`+`Secure` with real anti-CSRF tokens (synchronizer / double-submit / custom header), never rely on the cookie attribute alone. WebSocket CSRF is the adjacent trap: WebSockets inherit the app cookie jar, so a cookie-only-authenticated WebSocket endpoint that does not validate the `Origin` header on upgrade is CSRF-able from any WebView page. Two network-layer facts complete the picture: `network_security_config.xml` certificate pins do **not** protect WebView traffic (they apply only to native HTTP clients — `HttpsURLConnection`, OkHttp — while WebView uses the system store plus Chromium's rules), and a `WebViewClient.onReceivedSslError()` override that calls `handler.proceed()` unconditionally accepts MITM certificates (**CWE-295**, MSTG-NETWORK-4), a bypass Frida can force regardless of the app's implementation.

### Hybrid frameworks and real-world 1-click chains

Cordova, Capacitor, and React Native hand the JS layer a first-class native bridge, so an XSS in the web layer invokes every registered plugin — filesystem, camera, geolocation, native storage — which is categorically worse than web XSS, and the majority of that surface lives in third-party plugins (a supply-chain concern arguing for pinned dependencies with release cooldowns). Concrete instances: **CVE-2023-2507** (2023, CleverTap Cordova plugin ≤ 2.6.2, unsanitized deep-link input injecting JS into the main WebView context); Apache Cordova Android < 3.5.1 (remote JS bypassing the HTTP whitelist to open WebSockets to arbitrary servers); and `react-native-webview` inheriting CVE-2020-6506 when it permits navigation to arbitrary URLs. The class culminates in the Pwn2Own Ireland demonstrations of the deep-link → WebView → native pivot. In **2024**, NCC Group's Samsung Galaxy S24 chain used five bugs across several apps to install an arbitrary APK from a single link, anchored on Samsung Gaming Hub: **CVE-2024-49418** (Gaming Hub toggles JavaScript in a WebView without validating the URL) and **CVE-2024-49419** (loads the URL without validation), with a 302 redirect to an `intent://` URL launching arbitrary activities ([Samsung Galaxy S24 whitepaper](https://www.nccgroup.com/media/vodcuxpw/samsung-galaxy-s24-whitepaper.pdf)). In **2025**, Bugscale's Samsung Galaxy S25 chain reached install-and-launch of an arbitrary APK from a single malicious link. These validate the doctrine that a single URL-validation or JS-toggle mistake in a WebView is sufficient to escalate a web bug to full device compromise — treat every deep-link-supplied URL as untrusted, validate before loading and before changing any WebView setting, and block `intent://` and non-allowlisted schemes in `shouldOverrideUrlLoading()`.

## V. OAuth State and Token Theft via Mobile IPC

Mobile OAuth is where the deep-link and IPC weaknesses of Sections II–IV converge on a concrete, high-value asset: the authorization code and the access token. The native-app flow delivers the authorization response back to the app through an OS primitive — a custom URI scheme, a claimed-`https` App/Universal Link, or (wrongly) an embedded WebView — and every one of those primitives is a weaker origin channel than the browser's redirect. Two protocol controls, `state` (RFC 6749 §10.12, extended to native apps by RFC 8252 §8.9) and PKCE (RFC 7636), exist precisely to compensate, and the recurring failure mode is that one is missing, downgraded, or defeated by a channel that leaks the token alongside the code. The canonical defense is the AppAuth pattern (system browser + PKCE-S256 + validated high-entropy `state`); the residual risk is misconfiguration and platform gaps that no library can close.

### State parameter bypass — CSRF-based account linking

When a custom-scheme redirect flow omits or fails to validate `state`, an attacker mounts login CSRF / forced account linking: the attacker initiates their own authorization flow, captures their own `code`, then triggers the victim's app to open the callback — a background deep-link open suffices, no phishing needed — and the victim's app exchanges the attacker's code, binding the **attacker's identity to the victim's account** (or, symmetrically, the victim's identity into an attacker-controlled session). [RFC 6749 §10.12](https://www.rfc-editor.org/rfc/rfc6749#section-10.12) mandates `state`; [RFC 8252 §8.9](https://www.rfc-editor.org/rfc/rfc8252.html#section-8.9) extends the requirement to native apps. The mitigation is a cryptographically random ~128-bit value, session-bound, rejected on exact mismatch — and it is complementary to, not a substitute for, PKCE: neither alone is sufficient on mobile, because `state` defeats CSRF while PKCE defeats interception.

### PKCE downgrade — asymmetric server enforcement

PKCE binds the code to the initiating client's `code_verifier`, so an intercepted code is worthless — unless the authorization server enforces PKCE **asymmetrically**. The downgrade attack strips `code_challenge` from the authorization request; a server that then also skips the `code_verifier` check at token exchange re-opens the intercepted-code path for any party that captured the code (via scheme hijacking, ARP intercept, etc.). Three production CVEs confirm this is not theoretical:

- **CVE-2024-23647** (2024, authentik, PKCE downgrade; fixed 2023.8.7 / 2023.10.7).
- **CVE-2024-22258** (2024, Spring Authorization Server 1.0.0–1.2.2, PKCE downgrade affecting Authorization Code Grant; fixed 1.1.6 / 1.2.3; researcher [Pieter Philippaerts](https://spring.io/security/cve-2024-22258/)).
- **CVE-2025-4144** / GHSA-qgp8-v765-qxx9 (2025, Cloudflare `workers-oauth-provider` < 0.0.5, `handleTokenRequest` accepted `code_verifier` without requiring `code_challenge` at authorization time, CVSS 5.3; advisory published by [Kenton Varda](https://github.com/cloudflare/workers-oauth-provider/security/advisories/GHSA-qgp8-v765-qxx9)).

The governing rule is [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) §2.1.1 (OAuth 2.0 Security BCP, 2025; Daniel Fett co-author): servers MUST reject a token request containing `code_verifier` unless `code_challenge` was present in the authorization request, public mobile clients require PKCE unconditionally, and clients SHOULD use `S256`, currently the only challenge method that does not expose the verifier.

### Custom-scheme hijacking meets OAuth (the IPC-delivered code/token)

Both platforms allow duplicate custom-scheme registration with no ownership proof, so a co-installed malicious app can receive the OAuth redirect. On Android the attacker biases selection with a high `android:priority` (e.g. 999) or relies on the disambiguation chooser; on iOS, resolution is undefined when multiple apps claim the scheme (FireEye documented iOS URL-scheme hijacking / Masque in 2015). PKCE is the interception mitigation — but Mohamed Benchikh's ["One Scheme to Rule Them All"](https://blog.ostorlab.co/one-scheme-to-rule-them-all.html) (Ostorlab, 2023/2024) demonstrated the two ways it fails at scale: Facebook accepted `fbconnect://cct.com.<fake>` because the redirect **host was unvalidated** while sharing the legitimate `client_id`, and setting `login_hint` to the victim's email produced **zero-interaction** interception — affecting apps totalling 1B+ installs. PKCE also does not save flows that leak both `code` **and** `access_token` in the redirect fragment, because the token itself is exfiltrated regardless of code binding. **CVE-2024-26131** (2024, Element Android, deep link → WebView → login hijack) is a related intent-redirect variant. The only scheme-hijacking-resistant redirect mechanisms are App Links (`autoVerify` + `assetlinks.json`) and Universal Links (AASA) — but Universal Links **cannot serve as programmatic OAuth redirect targets on iOS** (they fire only on user taps, not programmatic opens; see AppAuth-iOS below), an unresolved platform gap that leaves PKCE + `state` as the sole iOS compensating controls. Fix at the server too: strict exact-match `redirect_uri` validation on scheme, host, and path, never loose host-prefix matching.

### IPC-adjacent credential exfiltration channels

Beyond the redirect itself, several OS-level side channels lift OAuth codes and tokens. **Clipboard/pasteboard sniffing:** Android < API 29 allowed any background app to register `ClipboardManager.addPrimaryClipChangedListener()` and silently read every copied item — 2FA codes, authorization codes, passwords; Android 10 restricted reads to the foreground app/default IME, 12 added a toast, 13 auto-clears; iOS < 14 allowed silent background `UIPasteboard.general` reads, iOS 14 added a post-hoc banner (data already read), iOS 16 introduced the first pre-access permission prompt (with consent-free bypasses via long-press paste, Cmd+V, and `UIPasteControl`). The fixes are `ClipDescription.EXTRA_IS_SENSITIVE` on Android and `UIPasteboard.withUniqueName()` on iOS, plus designing flows so codes are never manually copied ([MASTG-TEST-0073](https://mas.owasp.org/MASTG/tests/ios/MASVS-STORAGE/MASTG-TEST-0073/)). **MediaProjection consent bypass:** **CVE-2018-9524** (WithSecure/MWR, 2017 advisory; tapjacking overlay tricking the consent dialog, ~77% of devices at the time) and **CVE-2025-32322** (2025, improper input validation in `MediaProjectionPermissionActivity.onCreate`, Android 13–14, Wear OS bulletin 2025-09-01) both yield a valid MediaProjection token without genuine consent, enabling silent screen recording of OAuth tabs, 2FA codes, and autofill; sensitive screens must set `FLAG_SECURE`. **AccountManager cross-UID token sharing:** the platform does not enforce `AccountManager.KEY_CALLER_UID`, so any app that knows the correct `authTokenType` can claim a cached token unless the authenticator validates the caller signature itself. And **PendingIntent spoofing** — [arXiv:2603.02539](https://arxiv.org/pdf/2603.02539) (PendingIntent Provenance Confusion) — shows an app holding `NotificationListenerService` permission can steal and replay a partner app's PendingIntent to impersonate it in SDK-based auth callbacks, with no platform exploit required. Guidance: validate `KEY_CALLER_UID` against a signature allowlist, use short-lived minimally-scoped tokens, and never deliver auth callbacks via PendingIntent from notification-accessible contexts.

### Token storage, redirect-token exfil, and mutable-claim impersonation

Where tokens land after the flow matters as much as how they arrive. Chilik Tamir (MetaIntell, 2014) found the [Facebook SDK v3.15.0 stored access tokens in plaintext](https://thehackernews.com/2014/07/facebook-sdk-vulnerability-puts.html) — readable on iOS via a 5-second USB connection with no jailbreak, on Android via recovery — across 71 of the top 100 iOS apps and 31 of the top 100 Android apps; the fix is iOS Keychain / Android Keystore, never `SharedPreferences` or `NSUserDefaults`. Amol Baikar's 2020 [Facebook XD Arbiter finding](https://gbhackers.com/facebook-vulnerability/) ($55,000) chained a missing `X-Frame-Options` (the OAuth page was framable) with improper `window.parent` `postMessage` handling so a malicious site received the access token via the XD Arbiter event with **zero victim interaction**; the tokens were non-expirable and valid across Facebook, Instagram, Oculus, Netflix, Spotify, and Tinder — the fixes are `X-Frame-Options: DENY` on OAuth endpoints, strict `postMessage` origin validation, and token expiry/invalidation on password change. The **WKWebView-for-OAuth violation** (RFC 8252 §8.12) gives the app full JS access to the IdP page and, when developers work around iOS 14 ITP cookie purging with manual `WKHTTPCookieStore.setCookie` injection, opens an async race window (WebKit bug #213510) — the only correct answer is `ASWebAuthenticationSession` exclusively. Finally, **mutable-claim / client-confusion** impersonation: relying parties that identify users by the mutable `email` claim rather than the immutable `sub` are open to cross-tenant takeover (an attacker registers a token with the victim's email in an attacker-controlled Azure/IdP tenant — the "Login with Microsoft" class), and implicit-flow implementations without `client_id` verification accept foreign-audience tokens (Doyensec 2025, Salt Security 2023). Identify by `sub`, validate `aud`/`iss`/`azp` on every token, and prefer Authorization Code + PKCE over implicit.

### AppAuth as the canonical defense and its platform limits

[AppAuth-iOS and AppAuth-Android](https://appauth.io) implement the RFC 8252 defaults out of the box: external user-agent (`ASWebAuthenticationSession` / Chrome Custom Tabs, never an embedded WebView), PKCE with `S256`, auto-generated high-entropy `state` with automatic response validation, and OIDC `nonce`. The risk surface is entirely misconfiguration — omitting PKCE or passing a nil `CodeVerifierChallenge`, using a custom scheme without a paired App Link, or a server that does loose `redirect_uri` matching. The one hard platform limit is iOS: [AppAuth-iOS issue #396](https://github.com/openid/AppAuth-iOS/issues/396) documents that Universal Links do **not** fire on programmatic opens, so custom schemes remain the only usable iOS OAuth redirect mechanism and PKCE + `state` remain mandatory compensating controls (Daniel Fett's [app2app analysis](https://danielfett.de/2020/11/27/improving-app2app/) proposed the `.universalLinksOnly` + `ASWebAuthenticationSession` combination as the pragmatic workaround). The defense-in-depth stack is: PKCE-S256 + validated `state` + system browser + verified redirect links (App Links / Universal Links) + Keychain/Keystore storage.

## VI. Detection, Defense, and Semgrep Rule Guidance

This section maps the whole class to testable artifacts, states what the current tooling catches and where it is blind, and gives concrete AST-level rule shapes with their taint source/sink pairs and false-positive classes. The strategic point for rule authors: the highest-impact mobile CSRF-analogue bugs are **compound** — an exported manifest component *plus* a code-level dangerous sink — and most source-only, single-file SAST (including the shipped CodeQL Android queries) does not cross-reference `AndroidManifest.xml` against the Java/Kotlin sink, which is exactly the gap that let the EngageSDK-class vulnerability ship inside a merged library manifest.

### MASVS/MASTG mapping — the testing backbone

The [OWASP MASVS v2 / MASTG](https://mas.owasp.org/) catalog is the shared vocabulary. **MASVS-PLATFORM-1** (IPC and deep links) covers MASTG-TEST-0028 (Android deep links), -0026 (implicit intents), -0381 (insecure PendingIntent), -0393 (unverified App Links), -0070/-0395 (iOS Universal Links / AASA validation and handler input validation), and -0075 (custom URL schemes). **MASVS-PLATFORM-2** (WebView) covers MASTG-TEST-0031 (JS execution), -0032/-0077 (Android/iOS protocol handlers), -0033 (`addJavascriptInterface`), -0078 (`WKScriptMessageHandler`), -0037 (cache/credential cleanup), -0250/-0251/-0252/-0253 (content and file access), and MASTG-BEST-0011 (secure local file loading). Legacy mapping: MSTG-PLATFORM-5 → MASTG-TEST-0031; MSTG-PLATFORM-7 → MASTG-TEST-0033; the June 2025 checklist is current. Static analysis alone under-covers this class — pair rules with dynamic tooling: Drozer for exported-component attack-surface enumeration and crafted-intent testing, and Frida traces on `application(_:continue:restorationHandler:)` (Universal Link handler input) and `WebViewClient.onReceivedSslError` (TLS-bypass confirmation).

### Tooling landscape and its gaps

**Oversecured** analyzes compiled APK/AAB (no source), tracing attacker-controlled data from entry points (deep links, intents, QR codes, IPC, SMS) through all decompiled code paths **including merged SDK code** across 175+ Android / 85+ iOS categories — precisely the SDK/merged-manifest surface that source-only SAST misses. The shipped **CodeQL** `java/android` suite has three relevant queries — `webview-addjavascriptinterface` (CWE-79, severity 7.8), `unsafe-android-webview-fetch` (path-problem taint from intent extras to `loadUrl`, CWE-749), and `websettings-javascript-enabled` (7.8) — but **no first-party query cross-references the `AndroidManifest.xml` `exported` attribute against a `loadUrl(intent)` sink**, the manifest-aware compound gap that Oversecured and MobSF fill and that a well-constructed Semgrep ruleset with `join` mode can partially close. [IMQ Minded Security's 40+ MASTG-mapped Semgrep rules](https://blog.mindedsecurity.com/2023/10/semgrep-rules-for-android-application.html) (`mindedsecurity/semgrep-rules-android-security`, benchmarked on 280 apps / 111B+ downloads / 107,173 findings, ~382/app) cover `setAllowUniversalAccessFromFileURLs`, JS+bridge combinations, `onReceivedSslError` `proceed()`, and SSL-pinning misconfig, with the companion `insideapp-oss/mobile-application-security-rules` extending to Kotlin and Swift. The at-scale methodology is uniform: `apktool`+`jadx` decompilation → manifest-to-code correlation → taint analysis.

### Detectable AST patterns — Android IPC and deep links

**Manifest-level (CWE-926 / CWE-749).** Flag an exported component (`android:exported="true"`, or a component with an `<intent-filter>` and no explicit `exported` when the app targets < API 31) that lacks an `android:permission`, or is guarded only by a custom permission whose `protectionLevel` is `normal` (auto-granted) or `dangerous` (user-grantable) rather than `signature`. Separately flag a `BROWSABLE` `http(s)` `<intent-filter>` missing `android:autoVerify="true"` (unverified App Link, MASTG-TEST-0393). False-positive class: legitimately public launchers/share targets and components correctly guarded by a `signature`-level permission — the rule should not fire when a sibling `<permission android:protectionLevel="signature">` gates the component.

**Intent-redirection sink (taint).** Source: `getIntent().getParcelableExtra(...)` / `getIntent().getExtras()` yielding an `Intent`, or `Intent.parseUri(...)` (especially with `URI_ALLOW_UNSAFE`, the EngageSDK pattern). Sink: `startActivity` / `startService` / `sendBroadcast` / `bindService`. Fire when the source reaches the sink without an intervening component/selector strip or URI-grant-flag clear.

```
pattern-sources:  $I = (Intent)$X.getParcelableExtra(...)   // or Intent.parseUri($U, URI_ALLOW_UNSAFE)
pattern-sinks:    startActivity($I)  // startService / sendBroadcast / bindService
pattern-not:     $I.setComponent(...) | $I.setPackage(...) | IntentSanitizer(...).sanitize($I)
```

False-positive class: the forwarded Intent is constructed internally (not derived from an extra), or is passed through `AndroidX IntentSanitizer` / an explicit `resolveActivity()` allowlist before dispatch.

**PendingIntent (MASTG-TEST-0381).** Flag `PendingIntent.getActivity/getBroadcast/getService(...)` missing `FLAG_IMMUTABLE`, or using `FLAG_MUTABLE` combined with an **implicit** base Intent (no `setComponent`/`setPackage`). The mutable-implicit combination is the exploitable one; a mutable PendingIntent with a fully-explicit base is a much weaker finding.

**Host-validation weakness.** Flag `startsWith()` / `contains()` / `endsWith()` applied to a deep-link URL or host in lieu of exact match (bypassable with `https://trusted.com@attacker.com/` or `trusted.com.attacker.com`), and `Uri.getPathSegments()` / `getQueryParameter()` flowing unsanitized into HTTP request-path or URL construction (the path-traversal-to-ATO primitive; note `getPathSegments()` auto-decodes, so `%2F`/`..` must be rejected pre-decode).

### Detectable AST patterns — WebView and OAuth

**WebView danger combo.** The compound rule: `setJavaScriptEnabled(true)` + `addJavascriptInterface(...)` on an Activity that is exported in the manifest and calls `loadUrl()` with intent- or deep-link-derived input (MASTG-TEST-0033). Because the exported check lives in XML and the sinks in code, a high-fidelity rule needs manifest-to-code correlation (Semgrep `join` mode or a two-pass runner); the code-only sub-rule (JS enabled + interface + `loadUrl(getIntent()...)`) is still valuable at slightly higher FP cost. Also flag any `@JavascriptInterface`-annotated method whose name/body exposes auth or file operations (`getAuthToken`, `readFile`, exec-like), with `minSdk < 17` elevating it to the reflection-RCE class.

**File/SOP flags.** Flag `setAllowUniversalAccessFromFileURLs(true)`, `setAllowFileAccessFromFileURLs(true)`, and `setAllowFileAccess(true)` when JavaScript is enabled; on iOS flag `loadHTMLString(_:baseURL:)` with an empty or nil `baseURL` and **any** `UIWebView` usage at all.

**TLS bypass.** Flag `WebViewClient.onReceivedSslError(...)` overrides that call `handler.proceed()` unconditionally or without an explicit certificate comparison (CWE-295 / MSTG-NETWORK-3), and `shouldOverrideUrlLoading` implementations lacking a scheme/host allowlist (failing to block `intent://` and non-allowlisted redirects).

**iOS bridge/auth.**

```
pattern:      WKUserContentController().add($HANDLER, name: $N)
pattern-not:  ... message.frameInfo ... | ... message.frameInfo.securityOrigin ...
// plus: missing removeScriptMessageHandler on teardown; missing
// limitsNavigationsToAppBoundDomains=true / WKAppBoundDomains Info.plist entry
```

Flag OAuth performed in `WKWebView`/`UIWebView`/Android `WebView` rather than `ASWebAuthenticationSession` / Chrome Custom Tabs (RFC 8252 §8.12 violation), and AppAuth requests with a nil/absent `code_verifier` (PKCE) or a missing/unvalidated `state`. False-positive class for the bridge rule: first-party WebViews confined by `WKAppBoundDomains` and message handlers that do validate `frameInfo.securityOrigin` — the rule keys on the *absence* of origin validation, so include a `pattern-not` for the securityOrigin check.

### Defense-in-depth guidance and known limits

Never trust Intent contents for authorization: strip the component/selector and URI-grant flags with `AndroidX IntentSanitizer` and apply a `resolveActivity()` allowlist before forwarding; caller identity via `Binder.getCallingUid()`/`getCallingPackage()` is available **only** inside a `Service`/`ContentProvider` Binder transaction and is unavailable for Activity Intent delivery ([Chromium Android IPC guidance](https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/docs/security/android-ipc.md): "It is fundamentally impossible to determine the sender of an Intent, unless the Activity was started with `startActivityForResult`"). Create PendingIntents `FLAG_IMMUTABLE` with an explicit base; use explicit intents / `LocalBroadcastManager` for internal comms; require `signature` `protectionLevel` for intra-vendor IPC. For WebView: origin-gate bridges, load local content via `WebViewAssetLoader` / a real `https` `baseURL`, disable file access, remove handlers on teardown, opt into `WKAppBoundDomains` (top-level frames only, max 10 domains, third-party iframes unprotected), and never bridge remote content. For OAuth: AppAuth + PKCE-S256 + `state` + system browser + verified redirect links + Keychain/Keystore storage, strict exact-match `redirect_uri`, identify by `sub` not email, validate `aud`/`iss`/`azp`.

State the limits explicitly in rules and docs, because each is a place practitioners assume a control that is not there: **Android 12 (API 31) exported enforcement changes the default and forces an explicit `exported` declaration but adds no authorization** — `exported="true"` without a permission remains fully callable, SDK manifest merging can still introduce `exported=true`, and it does nothing for intent redirection, PendingIntent mutability, path traversal, scheme/deep-link hijacking, task hijacking, or WebView bridges; **`SameSite` does not stop intent injection** (an exported-Activity-driven WebView controls the URL origin directly).
